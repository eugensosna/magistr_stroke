[[ch-implementation]]
== Програмна реалізація та експериментальне дослідження

У розділі описано архітектуру ігрового застосунку, обґрунтовано вибір засобів реалізації та розглянуто реалізацію клієнтської і серверної частин.
Наведено структуру даних журналу сеансів, програмний інтерфейс сервера та засоби захисту даних пацієнта.
Викладено методику експериментального дослідження швидкодії застосунку, стабільності відстеження кисті і відтворюваності обчислених показників, а також наведено його результати.

[[sec-impl-architecture]]
=== Архітектура застосунку

Застосунок побудовано за клієнт-серверною архітектурою, у якій основну частину обчислень виконує браузер на пристрої пацієнта.
Такий розподіл випливає з вимог, сформульованих у підрозділі <<sec-task>>: обробка відео в реальному часі без встановлення програмного забезпечення та передавання на сервер в основному режимі лише числових показників.
Архітектуру застосунку наведено на рис. <<fig-architecture>>.

[[fig-architecture]]
.Архітектура ігрового застосунку
image::architecture.png[Архітектура застосунку,width=100%]

Застосунок складається з п'яти компонентів:

* клієнтська частина для пацієнта, яка отримує відео з вебкамери, визначає ключові точки кисті, обчислює кінематичні показники і виконує ігрову логіку;
* кабінет фахівця з реабілітації, у якому переглядаються результати сеансів і налаштовуються параметри вправ;
* сервер застосунку, що відповідає за автентифікацію, програмний інтерфейс для клієнтів, журнал сеансів і передавання кадрів у резервному режимі;
* сервіс розпізнавання, який у резервному режимі визначає ключові точки кисті за кадрами, отриманими від сервера застосунку;
* СУБД, у якій зберігаються облікові записи, результати калібрування і журнал сеансів.

В основному режимі (суцільні лінії на рис. <<fig-architecture>>) клієнт взаємодіє із сервером лише через REST API.
Після завершення серії вправ клієнт надсилає на сервер запис із показниками, склад яких визначено в підрозділі <<sec-model-session>>.
У резервному режимі (штрихові лінії) клієнт передає стиснуті кадри через з'єднання WebSocket, а сервер застосунку пересилає їх сервісу розпізнавання і повертає клієнту координати ключових точок.
Подальша обробка координат в обох режимах однакова, тому модель, розроблена в розділі <<ch-model>>, реалізується один раз на клієнті.

Сервіс розпізнавання виділено в окремий процес мовою Python, для якої MediaPipe має офіційний програмний інтерфейс <<google2026hands>>, тоді як сервер застосунку реалізовано мовою Java.
Відокремлення сервісу дає змогу масштабувати його незалежно від сервера застосунку, адже саме розпізнавання кадрів є найбільш ресурсомісткою операцією на сервері.

Клієнтську частину реалізовано на фреймворку Vue.js.
Він ґрунтується на стандартних HTML, CSS і JavaScript та надає декларативну компонентну модель програмування, яка спрощує розроблення інтерфейсів будь-якої складності <<vue2026>>.
Компонентний підхід дає змогу виділити ігрові сцени, вікно камери, панелі гри та елементи кабінету фахівця в окремі компоненти, а логіку відстеження і обчислення показників — у функції композиції (composables), які не залежать від конкретної гри.
Для статичної типізації використано мову TypeScript, що зменшує кількість помилок під час роботи з координатами і структурами даних сеансу.

Сервер застосунку реалізовано на Spring Boot, який призначений для створення самодостатніх Spring-застосунків, готових до промислової експлуатації <<spring2026boot>>.
Spring Boot містить готові модулі для побудови REST API (Spring Web), автентифікації і авторизації (Spring Security) та доступу до реляційної бази даних (Spring Data JPA), що скорочує обсяг інфраструктурного коду.

Для зв'язку сервера застосунку із сервісом розпізнавання обрано gRPC.
У gRPC клієнтський застосунок викликає метод серверного застосунку на іншій машині так, ніби це локальний об'єкт, а дані за замовчуванням серіалізуються за допомогою Protocol Buffers <<grpc2026>>.
Опис інтерфейсу сервісу у файлі Protocol Buffers дає змогу згенерувати клієнтський код для Java і серверний код для Python з одного опису.

Для передавання кадрів між браузером і сервером у резервному режимі використано протокол WebSocket, який забезпечує двобічний обмін даними між клієнтом і сервером через одне з'єднання <<fette2011>>.
На відміну від окремих HTTP-запитів, з'єднання WebSocket встановлюється один раз на весь сеанс, що зменшує накладні витрати на передавання кожного кадру.

==== Отримання відео та відстеження кисті

Відеопотік з вебкамери отримується засобами браузера (інтерфейс `getUserMedia`) і відображається в елементі `video`.
Кадри з цього елемента передаються моделі MediaPipe Hands, яка виконується в браузері у вигляді модуля WebAssembly.
Модель налаштовано на пошук однієї кисті, мінімальна впевненість виявлення і відстеження становить 0,5, що відповідає значенням за замовчуванням <<google2026hands>>.

Модель MediaPipe обробляє кадри послідовно, і поки триває обробка одного кадру, наступний не може бути переданий.
Тому кадри передаються в циклі, синхронізованому з оновленням екрана через `requestAnimationFrame`, а кадри, що надходять під час обробки попереднього, пропускаються.
Фрагмент реалізації цього циклу наведено в лістингу <<lst-frame-pump>>.

[[lst-frame-pump]]
.Цикл передавання кадрів моделі відстеження
[source,typescript]
----
const pump = async () => {
  pumpId = requestAnimationFrame(pump)
  const video = videoRef.value
  // MediaPipe обробляє по одному кадру,
  // поки модель зайнята, кадр пропускається
  if (isSending || !handsInstance || !video) return
  if (video.readyState < 2) return
  isSending = true
  try {
    await handsInstance.send({ image: video })
  } catch (err) {
    console.error(err)
  } finally {
    isSending = false
  }
}
pump()
----

Такий підхід автоматично узгоджує частоту обробки з продуктивністю пристрою: на потужному пристрої обробляється кожен кадр, а на слабкому частина кадрів пропускається без накопичення черги і зростання затримки.
Фактична частота обробки обчислюється за часовими мітками оброблених кадрів і використовується для вибору режиму роботи.

Режим роботи визначається за частотою обробки кадрів.
Якщо протягом інтервалу усереднення частота обробки на пристрої нижча за 25 кадрів за секунду, клієнт пропонує перейти до резервного режиму.
У цьому режимі кадр зменшується до роздільної здатності, достатньої для визначення ключових точок, стискається у формат JPEG або WebP і надсилається через з'єднання WebSocket.
Отримані від сервера координати передаються тому самому модулю попередньої обробки, що й координати, визначені локально.
Оскільки фільтр 1€ використовує фактичні інтервали між кадрами (підрозділ <<sec-model-filter>>), нерівномірне надходження координат через мережу не порушує фільтрацію.

private GameMotion mapToEntity(final GameMotionDTO dto,
                               final GameStats stats) {
    final GameMotion motion = new GameMotion();
    motion.setGameStats(stats);
    motion.setStartOffsetMs(dto.startOffsetMs());
    motion.setDurationMs(dto.durationMs());
    motion.setStartX(dto.startX());
    motion.setStartY(dto.startY());
    motion.setEndX(dto.endX());
    motion.setEndY(dto.endY());
    // перерахунок на сервері замість клієнтських значень
    final double distance = Math.hypot(
            dto.endX() - dto.startX(),
            dto.endY() - dto.startY());
    motion.setDistance(distance);
    motion.setSpeed(dto.durationMs() > 0
            ? distance / dto.durationMs() : 0);
    return motion;
}

[[sec-impl-server-security]]
==== Захист даних

Дані сеансів пов'язані зі станом здоров'я пацієнта, тому доступ до них обмежено.
Автентифікація реалізована за допомогою маркерів JWT, які подають набір тверджень про користувача в компактному вигляді, придатному для передавання між сторонами <<jones2015>>.
Після входу клієнт отримує короткостроковий маркер доступу і маркер оновлення.
Маркер доступу підписується алгоритмом HMAC-SHA512 і діє 10 хв, після чого клієнт отримує новий маркер за допомогою маркера оновлення.

Сервер не зберігає стан сеансу користувача: кожен запит до ресурсів `/api/**` перевіряється фільтром Spring Security за маркером доступу.
Відкритими є лише ресурси реєстрації, входу та перевірки працездатності сервера.
Паролі зберігаються у вигляді хешів, а запити з інших доменів обмежено політикою CORS зі списком дозволених джерел.
У робочому середовищі обмін даними між браузером і сервером відбувається лише захищеним з'єднанням HTTPS, а в резервному режимі — WebSocket поверх TLS.

Дослідження складалося з трьох експериментів.

. *Швидкодія.* На кожному пристрої виконувалися вправи протягом 5 хв в основному режимі, а на пристроях, де частота обробки нижча за 25 кадрів за секунду, — також у резервному режимі.
Фіксувалися частота обробки кадрів і затримка від захоплення кадру до отримання координат.
. *Стабільність відстеження.* Учасник утримував кисть нерухомо в заданих положеннях за різних умов освітлення.
Фіксувалися частка кадрів з виявленою кистю і тремтіння ключових точок без фільтрації та після фільтра 1€ з різними параметрами.
. *Відтворюваність показників.* Кожен учасник у кількох сеансах у різні дні виконував калібрування і серії кожної вправи.
Порівнювалися показники, отримані в різних сеансах.

Частота обробки кадрів обчислюється за формулою <<eq-exp-fps>>:

[[eq-exp-fps]]
[stem]
++++
F = \frac{K - 1}{t_K - t_1},
++++

де stem:[F] -- частота обробки кадрів, кадр/с;
stem:[K] -- кількість оброблених кадрів за інтервал вимірювання;
stem:[t_1], stem:[t_K] -- моменти отримання результатів для першого й останнього кадрів інтервалу, с.

Тремтіння ключових точок нерухомої кисті оцінюється за формулою <<eq-exp-jitter>>:

[[eq-exp-jitter]]
[stem]
++++
J = \frac{1}{21} \sum_{i=0}^{20} \sqrt{\frac{1}{K} \sum_{n=1}^{K} \frac{\lVert P_{i,n} - \bar{P}_i \rVert^2}{s_n^2}},
++++

де stem:[J] -- середнє тремтіння ключових точок у частках масштабного множника кисті;
stem:[P_{i,n}] -- координати stem:[i]-ї ключової точки в stem:[n]-му кадрі;
stem:[\bar{P}_i] -- середнє положення stem:[i]-ї ключової точки за інтервал вимірювання;
stem:[s_n] -- масштабний множник кисті в stem:[n]-му кадрі.

Відтворюваність показника між сеансами оцінюється коефіцієнтом варіації середніх значень, отриманих в окремих сеансах, за формулою <<eq-exp-repro>>:

[[eq-exp-repro]]
[stem]
++++
R = \frac{\sigma_S}{\bar{X}_S} \cdot 100\,\%,
++++

де stem:[R] -- коефіцієнт варіації показника між сеансами, %;
stem:[\bar{X}_S] -- середнє значення показника за всі сеанси учасника;
stem:[\sigma_S] -- середнє квадратичне відхилення середніх значень показника в окремих сеансах.
