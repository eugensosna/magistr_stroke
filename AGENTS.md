# AGENTS.md — інструкції для AI-агентів

Репозиторій містить магістерську роботу (кваліфікаційну роботу магістра), написану в AsciiDoc.
З неї автоматично генерується DOCX, оформлений за ДСТУ 3008:2015, ДСТУ 8302:2015 і Наказом МОН № 40.

**Тема:** «Ігровий застосунок для дистанційної реабілітації пацієнтів з порушенням дрібної
моторики на основі технологій комп'ютерного зору».

**Мова роботи:** українська (академічний стиль). Анотація також англійською.

## Команди

```sh
uv run build.py                    # build/thesis-dev.docx (у контейнері podman/docker), з примітками рецензента
uv run build.py pdf                # DOCX + build/thesis-dev.pdf через LibreOffice у контейнері (з оновленим змістом)
uv run build.py check              # перевірка посилань, джерел, рисунків, таблиць
uv run build.py check --sort-bib   # впорядкувати джерела за першим посиланням
uv run build.py --release          # чистова версія без приміток: build/thesis-release.docx
uv run build.py --release pdf      # те саме + build/thesis-release.pdf
uv run build.py review             # перелік зауважень (відкриті / виправлені)
uv run build.py --version X        # версія документа (типово: короткий SHA коміту, «-dirty» за незакомічених змін)
```

Типовий режим — dev: зауваження рецензента потрапляють у DOCX як примітки Word.
Чистова версія без приміток збирається лише з `--release`.

Відкриті завдання позначаються рядком-коментарем `// TODO: ...` у будь-якому `.adoc`, зокрема в `config/attributes.adoc`.
`check` виводить їх перелік з номерами рядків. На результат перевірки вони не впливають, але перед здаванням роботи всі TODO мають бути закриті.

Після будь-якої зміни тексту запускайте `uv run build.py check`, а після суттєвих змін — `uv run build.py pdf`.
Перегляньте сторінки PDF (`pdftoppm -r 60 -png build/thesis-dev.pdf /tmp/p`) і переконайтеся, що верстка не зламалася.

## Структура

| Шлях | Зміст |
|---|---|
| `thesis.adoc` | головний файл, порядок структурних елементів (include) |
| `config/attributes.adoc` | дані титульного аркуша, тема, ПІБ, рік |
| `config/format.toml` | поля, шрифт, інтервали (вимоги кафедри) |
| `chapters/NN-*.adoc` | текст, один файл на структурний елемент або розділ |
| `chapters/95-references.adoc` | список використаних джерел |
| `images/*.png` | рисунки, що вставляються в роботу |
| `images/src/*.svg` | вихідні файли схем (редагуються вони, PNG генерується) |
| `tools/` | конвеєр збірки. Не змінюйте його без потреби |
| `build/` | результати збірки. Не редагуйте вручну, не комітьте |

| `90-conclusions.adoc` | Висновки | шаблон |

Що вже зафіксовано в розділах 1–2 і в рішеннях щодо реалізації та має узгоджуватися з подальшими розділами:

- **Відстеження кисті.** Застосовується MediaPipe Hands: 21 ключова точка у форматі 2,5D, звичайна вебкамера, основна обробка в браузері на пристрої пацієнта.
- **Показники.** Застосунок обчислює кути згинання суглобів пальців, відстань між кінчиками пальців, ступінь розкриття кисті, частоту і ритм рухів. Показники нормуються на розмір кисті, перед вправами проводиться калібрування.
- **Вправи.** Щипковий захват, протиставлення великого пальця, розкриття і стискання кисті, ізольовані рухи пальців. Складність адаптується до можливостей пацієнта.
- **Архітектура.** Вебзастосунок у браузері (без встановлення), сервер з журналом сеансів, кабінет фахівця. В основному режимі на сервер передаються лише числові показники. Якщо частота обробки на пристрої нижча за 25 кадр/с, вмикається резервний режим: кадри передаються на сервер через WebSocket (захищене з'єднання, без збереження), сервер повертає координати ключових точок.
- **Засоби реалізації** (описуються в розділі 3, підрозділ «Вибір засобів реалізації»; у розділах 1–2 фреймворки не згадуються). Клієнт і кабінет фахівця: Vue.js, MediaPipe Hand Landmarker (WASM), Canvas 2D. Сервер: Spring Boot (Spring Security, REST, WebSocket-шлюз, Spring Data JPA), PostgreSQL. Резервне розпізнавання: окремий сервіс на Python з MediaPipe, який викликається зі Spring Boot через gRPC (MediaPipe не має офіційного API для серверної Java). Схема: `images/src/architecture.svg`.
- **Модель (розділ 2).** Ізотропні координати, фільтр 1€, нормування на stem:[s = \lVert P_9 - P_0 \rVert], показники stem:[\varphi], stem:[\Phi_k], stem:[d_k], stem:[O], stem:[I_k], stem:[f], stem:[V], калібрування до stem:[u \in [0; 1]], скінченний автомат вправи, правило «два вгору — один вниз». Параметри (stem:[f_{c,\min}], stem:[\beta], пороги) добираються експериментально в розділі 3.
- **Завдання дослідження.** П'ять завдань, перелічених у підрозділі 1.5. Їх треба повторити у вступі й закрити у висновках.

## Правила написання (обов'язкові)

1. **Одне речення — один рядок.** Абзаци розділяються порожнім рядком. Так diff у git лишається читабельним.
2. **Нумерація автоматична.** Не пишіть номери розділів, рисунків, таблиць і формул вручну.
   Посилання оформлюються так: `рис. <<fig-id>>`, `табл. <<tbl-id>>`, `формулою <<eq-id>>`, `підрозділі <<sec-id>>`.
3. **Ідентифікатори** пишуться латиницею з префіксами: `ch-`, `sec-`, `fig-`, `tbl-`, `eq-`, `lst-`, `app-`.
   Кожен рисунок, таблиця, формула з номером і лістинг повинні мати посилання в тексті, причому посилання має стояти **до** самого об'єкта.
4. **Джерела.** Посилання пишеться як `<<id>>` (дає [n]) або `<<id,с. 15>>` (дає [n, с. 15]).
   **Ніколи не вигадуйте джерела, авторів, DOI, сторінки чи числові результати.**
   Кожне нове джерело перевіряйте через Crossref або офіційний сайт (див. skill `thesis-sources`).
   Факти з джерела переказуйте лише так, як вони сформульовані в його анотації або тексті.
5. **Стиль.** Академічний, безособовий («розглянуто», «запропоновано», «у роботі показано»), без «я» і «ми».
   Не використовуйте розмовних слів і калік з російської та англійської. Терміни мають бути сталими (див. глосарій нижче).
6. **Структура розділу.** Розділ починається вступним абзацом і завершується підрозділом «Висновки до розділу N» з нумерованими висновками.
7. Не змінюйте `tools/`, `config/format.toml`, `build.py`, `Containerfile` у межах завдання з написання тексту, якщо про це не просили.
8. Не комітьте без прохання користувача.

## Зауваження рецензента

Зауваження керівника зберігаються в `.adoc` рядками-коментарями безпосередньо перед реченням, до якого вони стосуються.
У типовій dev-збірці вони стають примітками Word до цього речення, а в release-збірку (`--release`) не потрапляють.

```asciidoc
// ЗАУВАЖЕННЯ (Коломоєць Г. П., 2026-11-05) до «RAPAEL Smart Glove»: Потрібне посилання на систему/виробника
// ЗАУВАЖЕННЯ [fixed] (Коломоєць Г. П., 2026-11-05) до «MusicGlove»: Потрібне посилання на систему/виробника
// ВІДПОВІДЬ: додано виробника (Flint Rehab) і посилання на сайт
```

- Виправивши зауваження, додайте `[fixed]` і рядок `// ВІДПОВІДЬ: ...`. Самі зауваження не видаляйте.
  У dev-збірці така примітка отримує текст «FIXED: ...» і позначається як закрита (resolved).
- Частина `до «...»` необов'язкова. Вона лише допомагає знайти місце в тексті.
- Розбір, перетворення і перелік зауважень реалізовано в `tools/review.py`.

## Skills

У `.claude/skills/` є такі skills:

- `thesis-write` — написання або редагування розділу чи підрозділу;
- `thesis-sources` — пошук, перевірка й оформлення джерел за ДСТУ 8302:2015;
- `thesis-figures` — рисунки (SVG → PNG), таблиці, формули;
- `thesis-review` — нормоконтроль: збірка, перевірки, огляд верстки і тексту.
